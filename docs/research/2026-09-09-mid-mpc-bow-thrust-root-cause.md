# Mid-MPC 最近中断与 −20 kN 侧推：根因诊断

## 后续实施：已证实并修复的方向域错误（最新状态）

用户继续排查后，本轮从静态样本深入到了真实1181秒分配输入，并修复一处此前同向策略引入的过强约束。下文初轮“只读”“未执行修复”为历史诊断阶段记录；当前最新结果以本节为准。

**根因：净纵向力符号被误当作主桨方向。** 净纵向作用量包含三主桨推力及双舵纵向力，`X = sum(T_main) + X_rudders`。请求减速产生负X，并不意味着所有主桨必须倒推；共同前推配合舵阻力可能满足负净X，并保留有效桨洗流。原实现按 `requested.surge_n < 0` 直接选倒推域，把这样的合法解排除了。用户要求是三主推尽可能同进退，并未要求主桨方向必须跟随净X符号。

初轮线性规划仅证明指定倒推域中某个请求不可行，不是全部共同方向域不可行的证明。不可将人工−20 kN样本的分析泛化到所有低速饱和。

### 实施和保护边界

- 将共同前推/共同倒推视为同一个分配问题的两个合法区域；同一力误差权重、同一上一拍指令连续性目标比较收敛候选。以前不同域裁剪后的种子不能作为两个不同的比较目标，因此统一保留上一拍参考，只把数值初值投影到各域。
- 两域共享原700次求值预算，每域最多350；无物理阈值/成功条件放宽。只有证明另一域的最低连续性代价已不可能优于当前解时才剪枝，避免每拍无效搜索。
- 三主推仍不混向；实际换向仍全部过零并遵守原变化率。未改20 kN侧推上限、速度禁用逻辑、船模、PID参数或MPC安全约束。
- 工况trace新增PID限幅后请求、P/I/D/前馈、分配实现量与残差。旧`controller_request`字段仍代表raw，兼容已有读取方。

## 先回答：为什么使用侧推

是低速工况。`FCB45Allocator.allocate` 按船体速度减海流后的平面相对水速计算侧推权限，不按 Mid-MPC 场景名称决定。当前工程模型中：

- 相对水速 ≤1.5 m/s（2.92 kn）：全权限。
- 1.5–3.2 m/s：平滑减额；已禁用时须低于2.7 m/s（5.25 kn）才重新启用。
- ≥3.2 m/s（6.22 kn）：禁用。

每台原始上限 ±20 kN，再乘速度权限。负号表示船体负横向（左舷）推力，不能类比为三台纵向主机的倒车命令。以上是代码中的工程参数，不是已经实船验证的操作阈值。

本次负值冻结样本相对水体纵向速度 −0.09820 m/s、横向 +0.00599 m/s，合速度约0.0984 m/s（0.19 kn）；侧推权限1.0。三主推处于倒推域；当前模型不提供倒推桨洗流，负轴向入流时舵法向力斜率为零。因此该点的转向力矩来自主推差推和侧推，双舵贡献为零。这里的零舵效是当前模型结果，不能宣称实船倒车舵效绝对为零。

## 四项假设与检验

1. **需求超出联合能力**：独立线性规划，保持请求X/Y精确成立时，偏航可行范围仅 −113.834 至 +245.507 kN·m；请求却是 −357.506 kN·m，三轴同时实现无解。
2. **安装几何导致反向侧推**：两台均在船艏，x分别为+21.906、+23.406 m，仅隔1.5 m；`aft`指这一对中靠后的那台，不能误读为船艉侧推。等量反向20 kN只形成30 kN·m净力偶。两台同向虽有大力矩，却也产生很大横向合力，不能把各轴最大值拼成独立能力盒。
3. **热启动/优化病态**：对原负值样本，冷启动仍为−20 kN；按几何独立构建矩阵，TRF线性有界最小二乘与当前分配结果最大差仅2.5e−8 N。该点满推不是局部求解偶然失败。保持其余输入、只把偏航需求降至−100 kN·m，前侧推降到−7.738 kN。
4. **低速模型与上游能力脱节**：代码确认控制器偏航限幅是 `min(960000, 360000+2500*u_ground²)`，没有同时按当前X/Y请求、主推方向、相对水速、舵效和侧推权限构造可行域。该冻结点允许约360.741 kN·m，不能保证同一时刻X/Y/N可共同实现。抗积分饱和反馈存在，但并不把不可实现的当前需求变为可实现需求。

第三项还有明确边界：把偏航请求设为零，旧种子仍产生+20 kN，冷种子则约+1.393 kN。当前目标只惩罚力误差和相对上一拍指令变化，不惩罚绝对推力/轴功率，所以其他可行点也可能保留非必要的大侧推。不能根据“见到20 kN”就一律断言能力不足；本报告对原负值样本的能力不足由独立可行性检验确认。

## 纠正此前舍入描述的证据来源

此前“−20000.000000000007 N”来自 `probe_force_bounds.py` 第994个人工随机扰动样本：导航状态取自失败附近，但请求和种子经过扰动。它是精确边界问题的复现证据，不是原始在线失败帧。

原始 `bad-actuator.pkl` 捕获的是靠前侧推 **+20000.000000000004 N**。两者都只是20 kN附近几个ULP的数值越界。当前裁回原边界解决严格执行器检查抛错；不能用这7e−12 N解释为什么本来就用了20 kN。

既有 `verified-full/trace.jsonl` 中前侧推达到−20 kN共179步，首次约1245.2 s；这是此前完整重跑的实际执行量，区别于上述人工样本。该trace的`controller_request`记录的是PID的`raw_request`，不是限幅后送给分配器的请求；不能直接拿它与执行量相减就归因分配误差。

## 应先解决什么

先建立并核对“规划参考 → PID限幅输出 → 分配器静态可实现量 → 执行器实际量”的同帧能力证据，尤其低速、倒推、换向期间。区分数值收敛、静态可行、实际跟踪和终点到达。随后才讨论联合能力约束/参考整形，以及有资料依据的绝对控制努力或功率目标；侧推额定值、布局与倒车舵效仍需实船资料核对。

本轮是用户要求的根因调研，未执行技能第5阶段的新行为修复：禁止侧推、降低20 kN或改变残差权衡都不能从该现象直接推出。第6阶段交付为研究结论和可复现证据，不能声明控制缺口已修复。
