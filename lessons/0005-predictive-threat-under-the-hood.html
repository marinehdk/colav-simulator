核心模型：predictive-threat 不是一个分数函数。它是“物理事实 + 预测窗口 + 生命周期状态 + 证据身份”的组合。纯评估器不拥有状态；状态机不重新发明物理事实。

1. 输入：预测到底从哪里来？

2. 第一个事实层：DCPA/TCPA

对一个 target，先做相对运动：

r = p_target - p_own
v = v_target - v_own
range = ||r||
closing_speed = -(r · v) / ||r||
tcpa_signed = -(r · v) / ||v||²
tcpa_forward = max(0, tcpa_signed)
dcpa = ||r + tcpa_forward · v||

如果已有 PhysicalEncounterFacts，Threat Assessment 直接复用其中的 canonical geometry；没有时才在自己的 seam 计算。这样 Lifecycle 和 Threat Vector 不会因为各算一次而产生两套 DCPA/TCPA。

船体净空是：

hull_clearance = DCPA - ownship_radius - target_radius

注意：hull_clearance ≤ 0 是 response-time emergency 的候选依据；Ship Domain 本身不会替代 L4 continuous/swept safety。

3. 第二个事实层：Ship Domain 与窗口

V1 使用有前后、左右偏置的椭圆工程域。把目标位置投到自船 forward/starboard 坐标：

a = (fore + aft) / 2 + uncertainty_radius
b = (port + starboard) / 2 + uncertainty_radius
c = (fore - aft) / 2
scale = sqrt(((forward - c) / a)² + (starboard / b)²)

scale < 1 表示进入域，scale = 1 为 tangent，scale > 1 为 outside。uncertainty radius 来自 position covariance 最大特征值的平方根，再乘 profile multiplier；默认 profile 是 UNQUALIFIED，所以不能被误读为已经合格的安全域。

4. 第三个事实层：Threat Vector

ThreatAssessment.evaluate(request) 是纯函数式 public seam：按 TrackKey 排序，逐目标构造 immutable ThreatVector，再发布 snapshot/hash。向量至少同时携带：

  • 物理：range、closing speed、DCPA、signed/forward TCPA、hull clearance。
  • 预测：current/predicted domain、minimum scale、TDV/TDE、prediction basis。
  • 可信度：observation health、uncertainty、claim completeness、typed unavailable reasons。
  • 证据：track/prediction/domain/profile/physical-facts hashes。
关键防错：无 prediction 不等于“未来不会进入”；无 covariance 不等于“当前安全”；stale/unusable 不等于“目标消失”。代码让它们变成 typed UNKNOWN/UNQUALIFIED，而不是零值或 CLEAR。

5. 谁决定 Primary？不是 ThreatAssessment

Coordinator 先根据 vector 生成 PrimaryPriorityFact，再把它连同 canonical physical facts 交给唯一的 EncounterLifecycle。Lifecycle 保存 per-TrackKey episode、role、risk、commitment、passing side、Rule 17 stage、recovery guard 和 Primary challenger。

CLEAR无当前 obligation
CANDIDATE进入确认窗口
COMMITTED / ACTIVE承诺并执行
PAST_CLEAR净空 + route clear
RELEASED确认后恢复航线
REARMtombstone 后新 episode

Primary 的选择是 lexicographic，而不是 weighted average：

  1. response-time/hull emergency；
  2. Rule 17 MUST_ACT；
  3. committed + active；
  4. current domain violation；
  5. predicted domain violation；
  6. future severity/completeness；
  7. approaching TCPA、DCPA、range、TrackKey tie-break。

普通 challenger 需要经过约 10 秒的 physical-time hysteresis；emergency 或 MUST_ACT 可以 preempt。更重要：Primary 变化不能删掉 Lifecycle 的 required targets；这些 targets 最后成为 Aggregate Directive，供 Mid-MPC assembler 消费。

7. Conflict Graph：两类冲突，两个证据门槛

Direct window overlap：两个完整 Threat Window 的 [entry, exit]（没有 exit 时到 horizon end）发生时间相交，就生成 DIRECT_WINDOW_OVERLAP。这只说明多个 exposure 同期存在。

Plan-induced conflict：必须有 baseline、下一周期已 apply 的 accepted receipt、匹配的 target/prediction/profile hashes。然后比较 baseline 与 accepted ownship path；只有新 violation、TDV 至少提前 5 秒或 minimum scale 恶化至少 0.1，才生成 PLAN_INDUCED_CONFLICT。最后用 connected components 形成 transitive cluster。

8. 进入 UI 后发生什么？

mid_mpc_ipopt.py 把 snapshot 序列化进 planner algorithm_details.threat_management；gui_server.main._canonical_threat_projection() 只抽取 canonical snapshot/vectors/schedule/conflict graph；web_gui/modules/telemetry-projection.js 再做字段命名、Primary 标记和 null-safe display。

所以前端可以做单位格式化、卡片排序展示和 inspection context，但不能做：

  • 重算 DCPA/TCPA；
  • 按距离挑 Primary；
  • 从 trajectory 自己推 TDV/TDE；
  • 自行合并 conflict cluster；
  • 缺 snapshot 时推断 CLEAR。
