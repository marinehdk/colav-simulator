Ship 内部闭环

本课只回答：避碰算法得到什么输入，输出如何真正改变船舶状态。

完成标准：能独立画出 tracks -> references -> input -> state，并说明每个箭头由哪个子系统负责。

Ship 是子系统容器

Ship 同时持有 model、controller、guidance、sensors、tracker 和 COLAV。它不实现所有算法；它规定这些算法怎样交换数据。

感知与跟踪true states-> tracks
规划tracks + ownship-> references
控制reference[:,0]-> input
动力学state + input-> next state

第一道分叉：COLAV、guidance 或外部 actor

Ship.plan() 不是永远调用避碰算法：

  1. 存在 _colav：调用 ICOLAV.plan()，传入航路、自船状态、tracks、ENC、目标状态、扰动与船舶尺度。
  2. 不存在 COLAV、存在 _guidance：调用 LOS 等制导，仅根据名义航路生成 references。
  3. 两者都不存在：内部不生成 references；RL agent 等外部 actor 使用 set_references() 写入。
设计含义：比较避碰算法时，先确认实际走了 COLAV 分支，而不是 nominal guidance；训练 RL 时，先确认 remote_actor=True 确实绕过 Ship0 的内部 plan。

第二道边界：规划不是物理推进

Ship.plan() 只更新 self._references。随后 Ship.forward() 取第一列 reference，调用 controller 计算 input，再用四阶 Runge-Kutta 积分 model.dynamics，写回 self._state。

因此轨迹异常可能来自四处：tracker 给错目标状态、planner 给错 reference、controller 跟踪不住、model 参数或积分不对。只盯 planner 输出，无法完成闭环诊断。
