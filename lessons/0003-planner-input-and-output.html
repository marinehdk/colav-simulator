规划器输入与输出

本课消除一个危险混淆：预测轨迹、执行参考和真实轨迹不是同一个对象。

完成标准：看到 MPCSolution，能指出哪个字段立即执行、哪个字段描述未来、哪个字段证明求解质量。

先修正一个术语

你上一题的闭环判断正确，但“预测参考”应拆成两个对象：

预测predicted_trajectory规划器认为未来会怎样
执行参考control_reference当前交给 Ship 的 9x1 reference
控制输入controller output作用于模型的力或指令
真实状态state积分后实际得到的位置与速度

四者可能一致，也可能逐级偏离。画布上的预测线正确，只证明 planner trace 中的预测数据看起来合理，不证明控制器已执行，也不证明真实轨迹安全。

9x1 与 9xN 到底是什么

矩阵写法是“行数 x 列数”。这里每一列固定包含 9 个参考量：

[x_d, y_d, psi_d, u_d, v_d, r_d, ax_d, ay_d, rdot_d]^T

9x1：一个时刻的一列执行参考。9xN：N 个未来时刻的一列列参考；N 是预测时域采样点数，不是船舶数量。相邻列间隔由 horizon_dt_s 描述。

LOS course-speed 控制常只使用其中两个有效量，例如 [0, 0, chi_ref, U_ref, 0, 0, 0, 0, 0]^T。9 维是统一接口容器，不代表每种控制器都会使用全部九项。

PlannerInput：算法允许看见什么

CustomMPCAdapter 把旧式 ICOLAV.plan() 参数归一成强类型 PlannerInput：仿真时间、时间步、名义航路、自船 6 维状态、目标 tracks、ENC、目标状态、扰动、随机种子和船体尺度。

重要：算法通常读取 tracker 输出，不应偷偷读取目标船 truth。否则得到的是“完美感知条件下的规划能力”，不是完整系统能力。

MPCSolution：算法承诺什么

一次求解必须至少返回：

  • control_reference：固定 9x1，求解步立即返回给 Ship.plan()。
  • predicted_trajectory：9xN，携带预测未来并写入 PlannerTrace。
  • status 与 feasible：决定结果能否执行；不能只靠“有一条线”判断成功。
  • objective、iterations、constraints：解释求解质量。

在非求解时间步，adapter 执行 hold：若存在 control_trajectory，优先从中采样；否则从 predicted_trajectory 采样新的 9x1 reference。于是 solve_period_s 与 dt_sim_s 的关系直接影响执行。
